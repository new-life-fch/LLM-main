# 🔹 RAG检索思路

### **Step 1. 数据准备**

* 来源：HuggingFace `wikimedia/wikipedia` 数据集（现在的代码已将其下载到data文件夹中）
* 采样：按文章长度（近似热度）取 **100万\~200万篇文章** → **500万\~1000万 chunks**（先选择10000文章进行开发测试）
* 处理：

  * 清洗无效文章（stub、短文本）
  * 用 `BGE tokenizer` 切分（512 tokens / stride 128）
  * 保存 `title, url, text, chunk_id` 等 metadata

---

### **Step 2. Embedding & Indexing**

* 向量模型：`BAAI/bge-large-en-v1.5`
* 索引：FAISS HNSW（CPU内存存储 \~10M chunks）
* 存储：向量 + 原始文本 + metadata

---

### **Step 3. 检索流程**

1. 用户 query → BGE embedding
2. 向量库 HNSW 搜索 top-1000
3. **Reranker**：用 `BAAI/bge-reranker-large` 重新排序，保留 top-10（可调）
4. 计算 **相关性分数**（可取余弦相似度）

---

### **Step 4. Fallback 机制**

* **阈值判断**：

  * 如果 top-10 平均得分 < 0.3（可调），说明库中没找到足够相关内容。
  * 启用 **网络搜索**：

    * 调用 Wikipedia API / Bing / Google Custom Search
    * 检索最新相关页面
    * 抽取前 2–3 段落作为补充上下文（需要对内容进行清洗）

* **二次处理**：

  * 对抓取到的新内容再做 embedding & reranker
  * 如果合格（分数 > 阈值），加入检索结果
  * 把这些新内容 **缓存进本地向量库**，渐进式扩充语料

* **优化机制**：

  * 如果 top-5 平均得分 < 0.2 → 一定启用 fallback
  * 如果 0.2 ≤ score < 0.35 → 启用 fallback + 本地混合
  * 如果 ≥ 0.35 → 只用本地结果
* 给网络搜索加 **缓存层**（比如用 SQLite / Redis 记录 query→文档），避免重复请求慢。

---

### **Step 5. 生成阶段**（项目中相关功能已实现，只需检查）

* 构建指纹
* 检测冲突
* 激活编辑
* 生成回答

---
### **Step 6. 新增方案：优化指纹构建、冲突检测和激活编辑机制（用RAG系统举例，知识图谱系统也可以做相同处理，因此它们仍可以共用一个指纹构建、冲突检测和激活编辑机制）**
* 构建指纹时：
  - 输入用户问题 + 检索到的相关片段（假如检索到3个片段，需要构建三组指纹，每组1个片段）
  - 生成指定层的激活向量
  - 用户问题 + 检索片段的 **最后一个 token** 在中间到最后一层的激活向量
  - 当用户问题的相似度很高且片段id一致时，可以命中缓存，直接返回缓存的激活向量
* 推理时：
  - 输入只有用户问题
  - 生成指定层的激活向量
* 可以用 **指定层的最后一个 token 向量** 来做相似度对比：
  - 原因：
    - 中间层向量捕捉局部和结构特征
    - 高层向量包含更抽象语义
* 对比方法：
  - 取余弦相似度
  - 对推理时每个 token 的激活向量，计算与三组指纹的 **最大相似度** ，如果最大相似度小于冲突阈值，但检索到片段的最高分数很高，说明生成的 token 可能偏离参考语义 → 可能产生幻觉，需要进行编辑；如果最大相似度大于冲突阈值小于相似度阈值，说明生成的 token 可能与参考语义相关，但可能产生了偏离，需要进行编辑；如果最大相似度大于相似度阈值，说明生成的 token 与参考语义相关，且没有产生偏离，不需要编辑。
  - 设定阈值时希望可以根据最大相似度对应的检索片段分数（知识图谱为置信度）动态调整，比如如果最大相似度对应的检索片段分数很低，那么阈值需要调高；如果最大相似度对应的检索片段分数很高，那么阈值需要调低。
* 编辑方法：
  - **激活回退**：将当前 token 激活向量拉向最相似的参考指纹的激活向量
  - **重新采样**：使用回退后的激活向量继续生成后续 token
  - **激活加权**：希望可以根据最大相似度对应的检索片段分数，动态调整编辑强度
